The Delta

Server-rendered moves documents · Client-rendered moves state

The formal delta

Dimension Server-rendered (PRG) Client-rendered (API)
Formal name Hypermedia model — classic web / MPA SPA consuming a REST(ish) API
What travels HTML documents — the response IS the UI JSON representations — data only
State transition Navigation — every action loads a new document Function call — JS mutates the DOM in place
Who renders Server — render_page() Browser — renderTodos()
State between requests None in the browser; rebuilt from disk on every GET DOM + JS objects persist; synced via fetch
Client type Generic — any browser, zero custom code Custom client coupled to the API contract
After a form POST Server replies 303 + Location: / (PRG pattern) preventDefault() — no navigation at all

The formal framing

REST — Fielding, 2000

Formalizes the API version: resources (/api/todos), representations (JSON), a uniform interface (GET / POST / DELETE, status codes 201 · 400 · 404), and statelessness.

HATEOAS — hypermedia as the engine of state

The server-rendered version embodies this REST constraint: the form and links the server sends are the application's state machine, and the browser is a generic hypermedia engine.

UML sequence diagrams

The standard formal notation for message exchange between processes — lifelines, ordered messages, request/response arrows. Both diagrams above use it.

HTTP spec + named patterns

Request/response semantics are formally defined in RFC 9110/9112. Post/Redirect/Get is a named web design pattern; "SPA + JSON API" is its architectural counterpart.
